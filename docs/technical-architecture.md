# Technical Architecture

Status: active working architecture  
Scope: pre-launch funnel and the path toward the SaaS platform

## Decision summary

Use a TypeScript monorepo with three independently deployable applications:

- an Astro marketing site, statically generated by default;
- a React dashboard, added when product development begins;
- a TypeScript Cloudflare Worker API, introduced first as a very small lead-ingestion service and expanded with the product.

Use React inside Astro only for interactive islands. Build ordinary marketing sections, layouts, navigation, and content pages as Astro components so they ship little or no client-side JavaScript.

Use `pnpm` workspaces for package management and Turborepo for consistent local and CI tasks across applications. The applications may share contracts, design tokens, selected UI primitives, and tooling configuration, but they must remain independently buildable and deployable.

## Why this fits the product

The initial website is primarily content: positioning, use cases, provider qualification, trust material, and educational SEO pages. Its content will be the same for almost every visitor. Static generation is therefore the simplest and fastest rendering model.

SSR does not create an inherent SEO advantage over correct, pre-rendered HTML. It adds value when a response must vary per request—for example, authenticated account data, request-time personalization, or information that cannot wait for a rebuild. None of those are requirements for the initial funnel.

Astro pre-renders routes at build time by default and supports selectively opting individual routes into on-demand rendering later. Its official React integration supports rendering and hydrating React components. This lets us begin with static delivery without making the choice irreversible.

## Recommended repository structure

```text
ssm-usor/
├── apps/
│   ├── marketing/          # Astro: website, landing pages, content and funnel UI
│   ├── dashboard/          # React + Vite: authenticated SaaS application (later)
│   └── api/                # Node.js + TypeScript: leads first, product API later
├── packages/
│   ├── contracts/          # Shared schemas and API types; browser-safe
│   ├── design-tokens/      # Colors, typography, spacing and other brand tokens
│   ├── ui/                 # Selected React primitives shared deliberately
│   ├── config/             # TypeScript, linting and formatting configuration
│   ├── database/           # Schema, migrations and DB access; server-only (later)
│   └── document-engine/    # Generation/rendering abstractions; server-only (later)
├── docs/
├── package.json
├── pnpm-workspace.yaml
└── turbo.json
```

Only create a package once code genuinely needs to be shared. The directory tree is the destination, not a requirement to add empty packages during the first scaffold.

`marketing` is a clearer application name than `funnel`: the application will eventually contain the main website, campaign pages, articles, legal pages, and other acquisition content, while the funnel itself is one feature of it.

## Application boundaries

| Application      | Initial responsibility                                                   | Rendering                                            | Likely deployment                        |
| ---------------- | ------------------------------------------------------------------------ | ---------------------------------------------------- | ---------------------------------------- |
| `apps/marketing` | Positioning, qualification funnel, provider applications, articles       | Static Astro pages with isolated React interactivity | Static CDN at the main domain            |
| `apps/dashboard` | Authenticated multi-client SSM workspace                                 | Client-side React application; SEO is irrelevant     | Static assets at `app.<domain>`          |
| `apps/api`       | Lead ingestion, then authentication, business workflows and integrations | Cloudflare Worker                                    | Independently deployed at `api.<domain>` |

The marketing site must not import database code or server implementation details. The dashboard and marketing site may depend on browser-safe contracts. Only the API and server-side workers may depend on database and document-processing packages.

## Marketing site rendering rules

Keep these static:

- the homepage and campaign landing pages;
- solution and feature pages;
- industry/use-case pages;
- pricing or pilot-program information;
- articles, legislation explainers, comparison pages, and the glossary;
- legal and privacy pages.

Use React islands only where interaction materially improves the funnel, such as:

- the multi-step provider qualification form;
- a savings or ROI calculator;
- a clickable product walkthrough;
- advanced filters or interactive demonstrations.

Do not hydrate navigation, headings, benefit grids, testimonials, FAQs, or other static sections merely to keep them in React. Those remain local Astro components.

Add on-demand rendering only when a route requires request-time behavior. Astro supports mixing static and on-demand routes, so a later requirement does not require converting the entire site to SSR.

## Funnel and lead ingestion

The browser submits the qualification form to a narrow API endpoint. The endpoint should:

1. validate the request against a shared schema;
2. reject spam and rate-limit abuse;
3. save the lead and qualification answers;
4. preserve consent text/version, timestamp, referrer, and UTM attribution;
5. emit a conversion event only after successful persistence;
6. send the appropriate applicant and internal notifications;
7. return a stable outcome that supports safe retries without duplicate leads.

The form should collect enough information to distinguish an external SSM provider from an employer seeking services. A generic email-only waitlist can remain the secondary CTA, while the principal conversion is a qualified pilot application or discovery call.

The marketing browser must never connect directly to the production database. Starting with a small API endpoint gives us a durable trust boundary and a natural place for validation, auditability, rate limiting, and later CRM synchronization.

## SEO and performance baseline

The technical SEO baseline should include:

- Romanian-language, intent-specific pages with semantic HTML;
- unique titles and descriptions, canonical URLs, Open Graph metadata, and a generated sitemap;
- structured data only when it truthfully matches visible page content;
- content collections for articles and other repeatable SEO page types;
- optimized images, locally hosted fonts where practical, and strict limits on client JavaScript;
- redirects and URL ownership defined in source control;
- analytics and advertising tags loaded under the applicable consent rules;
- measurement of form starts, qualification completion, booked calls, and qualified-provider rate—not only page views.

Performance and accessibility should be enforced in CI with budgets rather than assessed only before launch.

## Dashboard direction

Use React with Vite for the authenticated application unless product discovery uncovers a real dashboard SSR requirement. The dashboard is a workflow application, not an SEO surface, so a client-side shell backed by the API is the simpler default.

The dashboard owns product interaction patterns such as client portfolios, employee records, document editing, tasks, reviews, and signatures. Marketing visual components should not dictate these workflows. Share design tokens and genuinely reusable primitives, not complete page components.

## API direction

Use a TypeScript Cloudflare Worker with the standard Fetch API. Keep routing and transport code thin so domain modules remain portable. Introduce a small Worker-native router only when the number or complexity of routes makes it useful.

Prefer a documented HTTP API with runtime-validated schemas and an OpenAPI description. Do not make a TypeScript-only RPC protocol the sole interface: the platform will need webhooks and integrations with email, electronic-signature, storage, billing, and possibly customer systems.

The full product backend will eventually need capabilities that do not belong in web requests:

- DOCX/PDF generation and rendering;
- email delivery and reminders;
- electronic-signature callbacks;
- legislation ingestion and update processing;
- AI document analysis;
- scheduled compliance checks and deadline notifications.

Model these as background jobs with durable retries and audit records. Cloudflare Queues or Workflows may orchestrate them. Because document conversion libraries and workers commonly require a normal server runtime, CPU-intensive or native conversion may run in a separately deployed EU-hosted Node.js/container worker.

## Shared-code rules

- `packages/contracts` contains schemas, identifiers, API payloads, and generated or hand-maintained client types. It cannot import database or Node-only code.
- `packages/design-tokens` is framework-neutral.
- `packages/ui` contains React primitives only when both a React island and the dashboard actually reuse them. Astro-native marketing components stay in `apps/marketing`.
- `packages/database` and `packages/document-engine` are server-only and must expose deliberate public entry points.
- Applications communicate through API contracts, not by importing another application's internal modules.
- Workspace dependencies use pnpm's `workspace:` protocol so a missing local package fails explicitly rather than silently resolving from a registry.

## Deployment shape

Keep the deployment units separate even though the source is in one repository:

```text
www.<domain> / <domain>  -> apps/marketing -> Cloudflare Workers Static Assets
app.<domain>             -> apps/dashboard -> Cloudflare Workers Static Assets
api.<domain>             -> apps/api       -> Cloudflare Worker
background jobs          -> queues/workflows -> portable processing workers
```

This permits the marketing site to deploy rapidly without redeploying the regulated product backend, and lets the API scale or change runtime independently. Hosting provider selection can wait until the landing page requirements, budget, and data-processing constraints are known.

## Staged implementation

### Stage 1 — validation funnel

Create:

- root pnpm/Turborepo configuration;
- `apps/marketing` with Astro, strict TypeScript, React integration, and sitemap support;
- a small `packages/contracts` package for lead validation;
- a minimal `apps/api` lead endpoint, or an equivalent independently deployed function using the same contract;
- analytics, consent handling, spam protection, and conversion attribution;
- automated build, type-check, lint, test, and accessibility/performance checks.

Do not create the dashboard, database abstraction, document engine, authentication, or a general-purpose design system during this stage.

### Stage 2 — clickable workflow validation

Add interactive product demonstrations or a disposable prototype. Keep prototype code out of the production dashboard unless it meets the platform's security and domain requirements.

### Stage 3 — SaaS foundation

Add `apps/dashboard`, authentication, multi-tenant authorization, PostgreSQL, audit logging, file storage, and the first narrow workflow selected by customer research. Expand `apps/api`; do not embed product logic in the marketing application.

### Stage 4 — document and compliance platform

Add background workers, document generation/versioning, electronic-signature integrations, tests and training workflows, and legislation/AI capabilities in the order established by validated provider demand.

## Decisions deliberately deferred

- cloud and regional hosting provider;
- authentication vendor or implementation;
- database ORM/query builder;
- job queue and worker infrastructure;
- document editor and rendering technology;
- electronic-signature provider and legal signature level;
- analytics and CRM vendors;
- whether API routing eventually warrants a Worker-native routing library.

These choices should be made against concrete requirements. They do not need to block the landing page.
